# 1단계: 요구사항

요청: $ARGUMENTS

## 현재 스펙
`specs/*/` 문서들의 맨 위 상태 줄(`> 상태: …`)과 tasks.md의 체크박스로 각 스펙의 단계를 확인한다.

## 템플릿
````markdown
# 요구사항: <기능 이름>
> 상태: 초안

## 개요
<무엇을, 누구를 위해, 왜 만드는지 2~3줄>

## 범위
- 포함: …
- 제외: …

## 요구사항

### 1. <요구사항 이름>
**사용자 스토리:** <역할>로서, <원하는 것>을 하고 싶다. 그래야 <얻는 가치>.

**인수 조건**
1.1 WHEN <사용자 행동·이벤트> THEN 시스템은 <결과>해야 한다(SHALL)
1.2 IF <오류·예외 조건> THEN 시스템은 <결과>해야 한다(SHALL)
1.3 WHILE <상태> 시스템은 <결과>해야 한다(SHALL)

### 2. <요구사항 이름>
…

## 가정
- <질문하지 않고 합리적으로 정한 것>

## 미해결 질문
- <사용자 답이 필요한 것>
````

## 절차
1. **기능 이름** — 영문 kebab-case로 정한다(예: `user-login`). 같은 이름의 스펙이 이미 있으면 새로 만들지 말고 그 문서를 이어서 다듬는다. 요청이 비어 있으면 무엇을 만들지 묻는다.
2. **맥락 파악** — README와 관련 코드를 필요한 만큼만 읽어 기존 구조와 용어에 맞춘다.
3. **질문** — 범위나 동작이 크게 달라지는 부분만, 최대 3개를 `AskUserQuestion` 도구로 한 번에 묻는다. 질문마다 선택지 2~4개를 주고, 추천하는 것을 맨 앞에 두고 "(추천)"을 붙인다. 사소한 것은 합리적으로 정하고 문서의 "가정"에 적는다.
4. **작성** — `specs/<기능>/requirements.md`를 위 템플릿대로 쓴다.
   - 요구사항마다 사용자 스토리 1개와, 테스트로 확인할 수 있는 인수 조건을 쓴다.
   - 정상 흐름뿐 아니라 오류·경계 상황도 인수 조건으로 쓴다.
   - 구현 방법(기술, 파일, 라이브러리)은 쓰지 않는다. 설계 단계에서 정한다.
5. **검토 요청** — 요구사항 목록, 가정, 미해결 질문을 짧게 보여주고, `AskUserQuestion` 도구로 선택지 박스를 띄워 묻는다(박스를 띄울 수 없으면 글로 묻는다).
   - 선택지: "승인하고 설계 단계로" · "승인만 하고 여기서 멈춤" · "수정할 부분 있음". 사용자는 기타 입력칸에 고칠 내용을 바로 적을 수도 있다.
   - 사용자가 박스 대신 대화로 답해도 똑같이 처리한다.
6. **반복** — "수정할 부분 있음"이면 무엇을 고칠지 듣고 문서를 고친 뒤 5번으로 돌아간다.
7. **승인** — 사용자가 승인을 고르면(또는 대화로 승인하면) 상태 줄을 `> 상태: 승인됨 (YYYY-MM-DD)`로 바꾼다.
   - "승인하고 설계 단계로"였으면 `spec-design` 스킬을 바로 실행한다. 사용자가 명령을 직접 입력할 필요는 없다.
   - "승인만"이었으면 멈추고, 나중에 "다음 단계 진행해줘"라고 하면 이어진다고 알린다.

## 규칙
- 사용자가 명시적으로 승인하기 전에는 상태를 `승인됨`으로 바꾸지 않는다.
- 이 단계에서는 코드를 쓰거나 고치지 않는다.
- 승인된 문서를 나중에 고치면 상태를 `초안`으로 되돌리고 다시 승인받는다. 이미 있는 design.md·tasks.md에 영향이 있으면 알린다.
