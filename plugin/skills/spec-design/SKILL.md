# 2단계: 설계

대상: $ARGUMENTS

## 현재 스펙
!`bash "${CLAUDE_PLUGIN_ROOT}/hooks/mem.sh" specs`

## 템플릿
````markdown
# 설계: <기능 이름>
> 상태: 초안
> 근거: requirements.md

## 개요
<요구사항을 어떻게 풀지 2~3줄>

## 현재 코드베이스
- <관련 파일·모듈과 역할, 재사용할 것>

## 아키텍처
<구성 요소와 흐름. 복잡하면 mermaid 다이어그램>

## 컴포넌트와 인터페이스
### <컴포넌트 이름> (`<파일 경로>`, 신규|수정)
- 책임: …
- 인터페이스: <함수 시그니처, API, 이벤트>

## 데이터 모델
<타입, 스키마, 저장 위치. 없으면 "변경 없음">

## 오류 처리
| 상황 | 처리 |
|---|---|

## 테스트 전략
- <무엇을 어떤 테스트로 확인하는지, 실행 명령>

## 요구사항 추적
| 요구사항 | 설계 요소 |
|---|---|
| 1.1 | … |

## 대안과 결정
- <고려한 대안, 고른 것과 이유>
````

## 절차
1. **대상 고르기** — 인자로 받은 기능을 쓴다. 인자가 없으면 위 목록에서 요구사항은 승인됐고 설계가 승인되지 않은 스펙을 고른다. 후보가 여럿이면 묻는다.
2. **관문 확인** — `specs/<기능>/requirements.md`의 상태가 `승인됨`이 아니면 멈추고 "요구사항이 아직 승인되지 않았습니다. `/spec-requirements`로 마무리해 주세요."라고 안내한다.
3. **조사** — requirements.md를 전부 읽고, 관련 코드를 충분히 읽는다: 비슷한 기능이 이미 있는지, 재사용할 헬퍼·패턴, 테스트 방식과 실행 명령.
4. **작성** — `specs/<기능>/design.md`를 위 템플릿대로 쓴다.
   - 요구사항을 모두 충족하는 가장 단순한 설계를 고른다. 기존 코드를 재사용하고, 요구사항에 없는 확장성은 넣지 않는다.
   - 모든 인수 조건이 "요구사항 추적" 표에 나와야 한다.
   - 고칠 파일과 새로 만들 파일을 경로로 적는다.
   - 해당 없는 섹션은 지우지 말고 "해당 없음"이라고 쓴다.
5. **검토 요청** — 핵심 설계 결정과 대안, 바뀌는 파일 목록을 짧게 요약하고 묻는다: "고칠 부분이 있나요? 괜찮으면 승인해 주세요."
6. **반복** — 피드백을 반영해 고친다. 요구사항 자체가 바뀌어야 하면 requirements.md를 고치고 그 문서도 다시 승인받는다.
7. **승인** — 사용자가 승인하면 상태 줄을 `> 상태: 승인됨 (YYYY-MM-DD)`로 바꾼다. `.claude-memory/`가 있으면 주요 설계 결정을 `decisions.md`에 기록한다. 다음 단계 `/spec-tasks <기능>`을 안내한다.

## 규칙
- 사용자가 명시적으로 승인하기 전에는 상태를 `승인됨`으로 바꾸지 않는다.
- 이 단계에서는 코드를 쓰거나 고치지 않는다.
- 승인된 문서를 나중에 고치면 상태를 `초안`으로 되돌리고 다시 승인받는다. 이미 있는 tasks.md에 영향이 있으면 알린다.
