# 3단계: 작업 목록

대상: $ARGUMENTS

## 현재 스펙
`specs/*/` 문서들의 맨 위 상태 줄(`> 상태: …`)과 tasks.md의 체크박스로 각 스펙의 단계를 확인한다.

## 템플릿
````markdown
# 작업 목록: <기능 이름>
> 상태: 초안
> 근거: requirements.md, design.md

- [ ] 1. <작업 제목>
  - 내용: <무엇을, 어느 파일에>
  - 완료 조건: <통과해야 할 테스트·확인 방법>
  - 요구사항: 1.1, 1.2
- [ ] 2. <작업 제목>
  - 내용: …
  - 완료 조건: …
  - 요구사항: …
````

## 절차
1. **대상 고르기** — 인자로 받은 기능을 쓴다. 인자가 없으면 위 목록에서 설계는 승인됐고 작업 목록이 승인되지 않은 스펙을 고른다. 후보가 여럿이면 묻는다.
2. **관문 확인** — `specs/<기능>/design.md`의 상태가 `승인됨`이 아니면 멈추고 "설계가 아직 승인되지 않았습니다. `/spec-design`으로 마무리해 주세요."라고 안내한다.
3. **읽기** — requirements.md와 design.md를 전부 읽는다.
4. **작성** — `specs/<기능>/tasks.md`를 위 템플릿대로 쓴다.
   - 작업 하나는 한 번에 검토할 수 있는 크기다(대략 파일 몇 개, diff 수백 줄 이내).
   - 앞 작업 위에 다음 작업을 쌓는 순서로 둔다. 작업이 하나 끝날 때마다 코드는 빌드되고 테스트가 통과하는 상태여야 한다.
   - 작업마다 확인할 수 있는 완료 조건을 쓴다. 테스트는 별도 작업으로 미루지 말고 해당 작업에 포함한다.
   - 코드로 할 수 있는 작업만 넣는다. 배포, 사용자 테스트, 성능 측정 같은 것은 넣지 않는다.
   - 모든 인수 조건이 어떤 작업의 "요구사항"에 최소 한 번 나와야 한다. 빠진 것이 있으면 작업을 추가한다.
   - 체크박스는 번호 매긴 작업 줄에만 쓴다(세부 항목은 일반 목록).
5. **검토 요청** — 작업 수와 순서, 빠뜨린 요구사항이 없다는 것을 짧게 보여주고 묻는다: "고칠 부분이 있나요? 괜찮으면 승인해 주세요."
6. **반복** — 피드백을 반영해 고친다.
7. **승인** — 사용자가 승인하면 상태 줄을 `> 상태: 승인됨 (YYYY-MM-DD)`로 바꾼다. 그리고 "구현 단계로 넘어갈까요?"라고 묻는다. 사용자가 진행하자고 하면(승인하면서 이미 진행을 요청했으면 묻지 않고) `spec-impl` 스킬을 바로 실행한다. 사용자가 명령을 직접 입력할 필요는 없다.

## 규칙
- 사용자가 명시적으로 승인하기 전에는 상태를 `승인됨`으로 바꾸지 않는다.
- 이 단계에서는 코드를 쓰거나 고치지 않는다.
